# Update Policy — VaultOS 프레임워크와 이 볼트는 어떻게 서로 갱신되는가

VaultOS는 두 개의 서로 다른 것으로 관리된다.

```
① VaultOS 프레임워크 repo   github.com/wook1990/vaultos.git   배포용 정본
② 이 볼트                  <클라우드 동기화 폴더 안, init.py --path로 지정한 경로>   ①을 init한 실제 운영 인스턴스
```

①을 `init.py`로 받으면 ②의 디렉토리 구조와 규칙 문서가 생성된다 ([[01_GOVERNANCE/ecosystem|ecosystem]] 참고). 그 뒤 ②는 실제로 쓰이면서 규칙이 다듬어지고, ①은 그 개선을 받아 다음 vault(또는 다음 기기)를 위한 정본으로 남는다. 이 문서는 그 두 방향을 어떻게 관리하는지 정한다.

## 1. 실제로 이미 벌어졌던 문제

2026-09-21 점검에서 확인된 것:

- ②의 `VAULTOS.md`는 `vaultos_version: 2.0.0`을 선언하고 있었는데, ①의 `VERSION` 파일은 `1.0.0`에 머물러 있었다 — 09-19 AIPM-Trace 이행 내용이 ①에는 이미 커밋돼 있었지만 버전 번호만 안 올라간 상태였다.
- ②에서 세션 중 직접 고친 큐레이션 규칙(Curator Grade/Watch Verdict 체계, Project Hooks 연결 방향, Inbox 파일명 확인 규칙) 3개 파일이 ①에는 전혀 반영되지 않은 채 남아 있었다.
- ①에는 `templates/project/*` 4개만 있고 그 외 11개 템플릿(`11_Inbox_Capture` 등)은 아예 없었다.

**즉 두 방향 다 손을 놓으면 조용히 벌어지는 드리프트다.** 이 문서 작성과 동시에 위 3가지를 정리했다 — 기록은 ①의 `CHANGELOG.md` (`v2.1.0`).

## 2. 버전은 ①의 `VERSION`이 정본이다 (SemVer)

| 단계 | 의미 |
|---|---|
| MAJOR | 구조·필수 계약이 바뀐다. 기존 방식으로 만든 볼트가 깨질 수 있다 |
| MINOR | 새 선택적 규칙·필드·템플릿이 추가된다. 기존 볼트는 그대로 동작한다 |
| PATCH | 문구·설명 보강, 오탈자, 문서 내 인덱스 정정 |

②는 `00_SYSTEM/vault-config.yaml`의 `framework_version`에 "마지막으로 정합화한 ① 버전"을 기록한다. 이 값과 ①의 실제 `VERSION`이 다르면 드리프트가 있다는 뜻이다 — 지금은 사람이 눈으로 비교해서 확인한다.

## 3. 어떤 파일이 "정본을 따라가는 파일"이고, 어떤 파일이 "이 볼트만의 것"인가

전부 다 ①→② 로 흘러야 하는 건 아니다. 2026-09-21 점검에서 실제로 확인된 세 가지 정당한 이유의 divergence가 있었다 — 이걸 착각해서 무작정 덮어쓰면 오히려 정본을 망가뜨린다.

| 유형 | 예시 | 처리 |
|---|---|---|
| **인스턴스 값 치환** | `<you>` → `wook1990`, `<repo>` → 실제 로컬 경로 | ②만 값이 채워져 있는 게 정상. ①은 placeholder를 유지한다 |
| **인스턴스 전용 링크** | ①은 공개 `docs/CASE-STUDY.md` 링크, ②는 이 볼트 안의 위키링크 | ②가 가리키는 문서가 이 볼트에만 있는 인스턴스 기록이면, ①에 같은 경로가 있을 리 없으니 다르게 쓰는 게 맞다 |
| **개인 전용 콘텐츠** | QT 노트 템플릿, worklog(활성화 여부 미결정), 특정 프로젝트 전용 에이전트(`02_강의_기획자_에이전트`) | ①에 절대 포함하지 않는다. 프레임워크는 범용이어야 한다 |
| **진짜 규칙 개선** | Curator Grade 체계, Project Hooks 연결 방향, 파일명 확인 규칙 | 이런 것만 ①로 백포트한다 |

파일을 비교했을 때 다르다고 바로 "①이 뒤처졌다"고 판단하지 않는다. 위 표의 앞 세 유형인지 먼저 확인한다.

## 4. 절차 — 지금은 사람이 트리거하는 수동 정합화다

`vaultos update` / `vaultos backport` 커맨드는 아직 없다. `vaultos-health.md`의 MVP 원칙과 같은 이유로, 실제로 두세 번 더 이 작업을 손으로 해보고 나서 반복되는 부분만 스크립트로 만든다. 지금은:

1. ①을 최신으로 pull 한다.
2. `00_SYSTEM/`, `01_GOVERNANCE/`, `04_AGENTS/`, `05_OPERATIONS/`에서 ①과 ②에 같은 경로로 있는 파일을 diff한다.
3. 다른 파일마다 위 §3 표로 분류한다.
4. **① → ②로 갱신할 것**: ②가 그 파일을 손댄 적이 없으면 새 버전으로 덮어쓴다.
5. **② → ①로 백포트할 것**: §3의 "진짜 규칙 개선"이면 ①에 반영하고 `CHANGELOG.md`에 적고 `VERSION`을 올린다.
6. ②만 있고 ①에 없는 파일은 §3 분류를 거쳐, 범용이면 ①에 새로 추가한다 (2026-09-21에 템플릿 11개가 이렇게 추가됐다).
7. `00_SYSTEM/vault-config.yaml`의 `framework_version`을 ①의 새 `VERSION`으로 갱신한다.
8. ①에 커밋한다. **push는 별도로 확인받는다** — 로컬 커밋과 원격 반영은 다른 수준의 되돌리기 난이도를 가진다.

git이 ② 안에서 동작하지 않으므로(`sync-policy.md` §0, WSL 9p 마운트 chmod 미지원) 3-way merge 자동화는 불가능하다. 파일 해시나 수동 diff로 "손댄 적 있는지"를 판단한다.

## 5. 자동화하지 않는 이유

`vaultos-health.md` §5의 재발 경보와 같다 — 이 볼트의 실패 모드는 구조 부족이 아니라 **운영되지 않는 자동화의 과잉 생성**이다. `vaultos update` 스크립트를 지금 만들면, 그 스크립트가 §3의 세 가지 정당한 divergence를 구분 못 하고 인스턴스 값을 정본으로 덮어쓰거나 개인 전용 콘텐츠를 프레임워크에 섞어 넣을 위험이 실제로 있다 (오늘 점검에서도 처음엔 "다르면 다 백포트 대상"으로 보였다가 표의 앞 세 유형이 훨씬 많다는 게 diff를 직접 봐야 드러났다). 손으로 두세 번 더 해보고, 패턴이 안정되면 그때 스크립트로 만든다.
