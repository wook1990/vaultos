# Case Study — 이 프레임워크가 나온 배경

VaultOS는 설계 이론에서 나오지 않았다. **2년 가까이 운영하다 두 번 무너진 개인 볼트를 전수 조사한 결과**에서 나왔다.
아래 수치는 2026-09-19에 실측한 값이다. 프레임워크의 각 규칙이 어떤 실패에 대응하는지 보여준다.

## 조사 시점 규모

| 영역 | md 파일 |
|---|---|
| 시스템·정책 문서 | 73 |
| 지식 (inbox/fleeting/permanent) | 157 |
| 프로젝트 6개 | 138 |
| 참고자료 | 436 |
| **합계** | **850** |

## 발견 1 — 중복 문서 61개

md5 기준 **내용이 완전히 같은 파일 61개**가 존재했다(고유 776 / 전체 837). 전량이 한 폴더 안에서 발생했다.

같은 강의 자료가 **4개 트리에 병존**했다.

```
00_Curriculum_Path/         71개  ← 인덱스 A가 "여기가 전부"라고 주장
26_..._V2/                  74개  ← "작업 원본"
27_..._최종_제공본/         146개  ← 인덱스 B가 "여기만 보면 됨"이라고 주장
28_..._제작_정리본/         139개  ← V1 + 백데이터
```

`00_Curriculum_Path`의 71개 중 **40개가 다른 트리와 바이트 단위로 동일**했다.

> **대응 규칙**: 같은 책임을 가진 문서를 두 곳에 두지 않는다. 정본 하나를 지정하고 나머지는 `99_ARCHIVE`로 내린다.

## 발견 2 — 인덱스끼리 서로 다른 정본을 지시

같은 폴더의 두 인덱스 문서가 **서로 다른 곳을 정본이라고 말하고 있었다.** 둘 다 틀린 말이 아니었다. 시점이 달랐을 뿐이다.

더 심각한 것은 **볼트 자체의 정의 문서가 4곳에 존재**했다는 것이다. 새 에이전트가 들어오면 무엇이 현재 기준인지 판별할 방법이 없었다.

> **대응 규칙**: `00_SYSTEM/VAULTOS.md` 하나만 최상위 정의다. 루트의 에이전트 진입 파일은 **내용을 복사하지 않고 이것을 가리키기만 한다.**

## 발견 3 — 고아 문서 34%

**850개 중 283개(34%)가 어떤 문서에서도 링크되지 않았다.**
템플릿은 **17개 중 15개가 고아**였다 — 만들어졌지만 실제 운영에서 호출되지 않았다.

> **대응 규칙**: 구조 검사에 broken link와 고아 탐지를 넣는다(`tools/vaultos_health.py`). 사람이 몇 달 뒤에 발견하게 두지 않는다.

## 발견 4 — 활동이 2개월 만에 멈췄다

md 수정일 분포:

```
4월  489개 (전체의 58%)   ← 폭발적 제작
5월  162개
6월    4개                ← 사실상 중단
7월   10개
8월   47개
9월  125개                ← 재개
```

4~5월에 만든 것 중 실제로 살아남은 것은 **`inbox → fleeting` 파이프라인과 프로젝트뿐**이었다.
같은 시기에 만든 `Areas`(빈 README 11개), `QT`(3건 후 정지), 템플릿 대부분은 **만들어졌지만 운영되지 않았다.**

> **이것이 이 프레임워크의 핵심 전제다.**
> **실패 모드는 "구조 부족"이 아니라 "운영되지 않는 구조의 과잉 생성"이다.**
>
> 대응 규칙:
> - `personal-light`는 **파일 1개**로 시작한다. 시작 마찰이 높으면 안 쓰게 된다
> - 자동화(Drift 탐지, Event Log, Dashboard)는 **필요해진 시점에** 만든다
> - 새 구조를 추가하기 전에 *"이미 만들었다가 방치한 것과 무엇이 다른가"*에 먼저 답한다

## 발견 5 — 프로젝트당 파일 53~115개

프로젝트마다 자동 생성된 것:

- `30_Tracking/` 아래 **미러 파일 15개** (Tasks/Issues/Decisions/Releases/Requirements/TestCases/Risks/Artifacts/Policies/AgentMemory/Capacity/Deliverables/Approvals...)
- 거버넌스 문서 10개 이상 (Control Tower, Grill Gate, Requirements Traceability, Test Matrix, Capacity Plan, Team Approval Gates...)

미러는 git 저장소의 `tracker/*.yaml` **하나를 마크다운 15개로 쪼개 복제한 것**이었다.
한 프로젝트의 tracker에는 **"미러 파일을 동기화하는 task"**까지 들어 있었다 — 시스템이 자기 복제 구조를 유지하기 위한 일을 스스로 만들어내고 있었다.

정리 후: 프로젝트당 9~28개.

> **대응 규칙**: Zone 분리. **"무엇을 했는가"는 repo, "왜 그렇게 하기로 했는가"는 볼트.**
> tracker는 git에 있고, 볼트는 그것을 **복제하지 않고 가리킨다.**

## 발견 6 — 클라우드 동기화 충돌

한 프로젝트에서 **5개월간 방치된 동기화 충돌 사본**을 발견했다.

```
20_Phase_Log_Mirror (conflict 2026-04-21-19-48-33).md
```

원인은 명확했다. 자동화가 **여러 개의 작은 파일에 연속적으로 쓰고** 있었고, 클라우드 동기화는 병합을 하지 않는다.

> **대응 규칙**:
> - `init`이 저장소 백엔드를 묻고, 병합 지원 여부에 따라 규칙 강도를 조정한다
> - 에이전트는 **세션 경계에서만** 쓴다. 연속 자동 반영을 금지한다
> - 충돌 확률 = `동시 접근 × 쓰기 빈도 × 파일 수`. 세 값을 모두 낮게 유지한다

## 발견 7 — 실제 유실 위험은 0이었다

가장 걱정했던 프로젝트(리서치 문서 80여 건 + 코드)를 삭제하기 전에 대조했다.

| | 개수 |
|---|---|
| git 저장소의 `docs/` | 88 |
| 볼트에 있던 `docs/` | 44 |
| **볼트에만 있던 것** | **0** |

볼트 사본은 저장소의 **부분집합, 그것도 넉 달 묵은 스냅샷**이었다.

> **이것이 Zone 분리의 실증이다.** 볼트가 저장소를 복제하면 항상 뒤처지고, 결국 "어느 쪽이 맞나"를 사람이 판단해야 한다.

## 검증

이 프레임워크로 실제 프로젝트 하나를 처음부터 끝까지 돌렸다.

```
INTAKE → Requirement ×3 → ADR → tracker(repo) → Task ×3
→ 구현 → 검증 → Issue 2건 발견·수정 → Evidence → Done
```

그 과정에서 **구현이 정책 문서와 어긋난 것을 스스로 잡아냈다.** 정책은 파일 3개를 요구했는데 검사기는 1개만 검사하고 있었다.
Requirement → 구현 → 검증을 거치지 않았다면 그대로 넘어갔을 것이다.

구조 검사 도구는 **자기 자신의 버그도 찾았다.** 회고 문서가 깨진 링크를 *예시로 인용*한 것을 실제 링크로 오탐했다.

## 요약

| 규칙 | 어떤 실패에서 나왔는가 |
|---|---|
| 정본은 하나 | 정의 문서 4곳, 인덱스 충돌 |
| 볼트는 repo를 복제하지 않는다 | 미러 15개, 44/88 부분집합 |
| 시작은 파일 1개 | 4월 489개 → 6월 4개 |
| 자동화는 나중에 | 템플릿 17개 중 15개 고아 |
| 세션 경계에서만 쓴다 | 5개월 방치된 충돌 사본 |
| 끝난 것은 끝났다고 적는다 | 해소된 과제가 목록에 남아 할 일이 쌓인 것처럼 보임 |
